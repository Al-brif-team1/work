# AI Assistant

Python-ядро для анализа внешних брифов заказчиков на студенческие проекты
«Мастерской».

Система загружает и нормализует один бриф, отсекает пустой или опасный ввод до
LLM, извлекает структурированные факты с помощью LLM, детерминированно проверяет
полноту данных, выполняет один объединённый LLM-этап `Assessment`, применяет
настраиваемые правила арбитража, генерирует уточняющие вопросы по шаблонам, при
необходимости формирует MVP-план и возвращает структурированный JSON.

## Архитектура

Приложение — CLI без сервера и базы данных: один запуск обрабатывает один бриф и печатает JSON
в stdout. Бизнес-логика живёт в конвейере этапов, всё остальное — обслуживающие слои.

```text
              ВХОД
   app/main.py — CLI: --text | --file | --normalize-only
              │
              ▼
   ┌────────────────────────────────────────────┐
   │ ПРИЁМ БРИФА       app/input/brief_input.py │
   │ BriefInputFactory → BriefInput             │
   │ текст или UTF-8 файл, нормализация пробелов│
   └────────────────────────────────────────────┘
              │
              ▼
   ┌────────────────────────────────────────────┐      ┌──────────────────────────┐
   │ КОНВЕЙЕР     app/pipeline/orchestrator.py  │      │ КОНФИГУРАЦИЯ             │
   │ BriefAnalysisPipeline                      │◀─────│ app/config/settings.py   │
   │ этапы над общим AIContext (frozen-модель:  │      │   Settings ← .env        │
   │ этап не меняет контекст, а возвращает      │      │ config/criteria.yaml     │
   │ новую версию)                              │      │ config/traffic_light.yaml│
   │ базовые классы: BaseStage, BaseLLMStage    │      │ config/question_*.json   │
   └────────────────────────────────────────────┘      │ config/field_titles.json │
        │                              │               └──────────────────────────┘
        │ LLM-этапы                    │ все этапы
        ▼                              ▼
   ┌──────────────────────────┐   ┌──────────────────────────┐
   │ LLM-СЛОЙ      app/llm/   │   │ НАБЛЮДАЕМОСТЬ            │
   │ LLMClientFactory         │   │ app/tracing/             │
   │ OpenRouterLLMClient      │   │ LangfuseTracingClient    │
   │   OpenAI-совместимый API,│   │   или NoOpTracingClient, │
   │   адрес задаётся в .env  │   │   если ключи не заданы   │
   │ LLMRunner: повторы,      │   │ LoggerFactory → logs/    │
   │   таймаут, разбор JSON   │   │ диагностика в stderr     │
   │   по схеме               │   └──────────────────────────┘
   │                          │
   │ ПРОМПТЫ    prompts/*.md  │
   │ PromptManager            │
   └──────────────────────────┘
        │
        ▼
   ┌────────────────────────────────────────────┐
   │ РЕЗУЛЬТАТ  app/schemas/final_result.py     │
```

Бизнес-правила — критерии, обязательные поля, запрещённые темы, правила арбитража, светофор
и шаблоны вопросов — вынесены в `config/` и не зашиты в промпты или Python-логику.
Разбор каждого файла и класса — в [docs/architecture_explained.md](docs/architecture_explained.md).

## Пайплайн

```text
   ВХОД: BriefInput
        │
        ▼
   ┌──────────────────────────────────────────────────────────┐
   │ AIContext.from_brief()                          [PYTHON] │
   │ контейнер состояния: бриф + конфигурация criteria.yaml   │
   └──────────────────────────────────────────────────────────┘
        │
        ▼
   ┌──────────────────────────────────────────────────────────┐
   │ Extractor                                       [LLM #1] │
   │ извлекает факты: цель, задачи, направление, материалы,   │
   │ ожидаемый результат, ограничения, сроки → ExtractedBrief │
   └──────────────────────────────────────────────────────────┘
        │
        ▼
   ┌──────────────────────────────────────────────────────────┐
   │ CompletenessCheckStage                          [PYTHON] │
   │ сверяет факты с required_fields из criteria.yaml:        │
   │ что есть, чего не хватает, что нужно уточнить            │
   └──────────────────────────────────────────────────────────┘
        │
        ▼
   ┌──────────────────────────────────────────────────────────┐
   │ AssessmentStage                                 [LLM #2] │
   │ запрещённая тема → готовый результат без вызова модели;  │
   │ иначе LLM даёт оценки критериев, риски и светофор,       │
   │ статусы светофора пересчитываются кодом по               │
   │ traffic_light.yaml (red > unknown > yellow > green)      │
   └──────────────────────────────────────────────────────────┘
        │
        ▼
   ┌──────────────────────────────────────────────────────────┐
   │ TrafficLightDiagnosticsStage                       [CLI] │
   │ печатает разбор светофора в stderr, JSON не меняет       │
   └──────────────────────────────────────────────────────────┘
        │
        ▼
   ┌──────────────────────────────────────────────────────────┐
   │ DeterministicArbiterStage                       [PYTHON] │
   │ правила арбитража из criteria.yaml дают final_status:    │
   │ REJECT | CLARIFY | SIMPLIFY | MENTOR_REVIEW |            │
   │ ACCEPT_WITH_CLARIFICATIONS | ACCEPT                      │
   └──────────────────────────────────────────────────────────┘
        │
        ▼
   ┌──────────────────────────────────────────────────────────┐
   │ TemplateQuestionGeneratorStage                  [PYTHON] │
   │ вопросы из question_templates.json плюс вопросы          │
   │ по жёлтым задачам светофора                              │
   └──────────────────────────────────────────────────────────┘
        │
        ▼
   ┌──────────────────────────────────────────────────────────┐
   │ MVPPlannerStage                                 [LLM #3] │
   │ вызывает модель, только если final_status == SIMPLIFY,   │
   │ иначе plan = None и обращения к LLM нет                  │
   └──────────────────────────────────────────────────────────┘
        │
        ▼
   ┌──────────────────────────────────────────────────────────┐
   │ ResponseWriterStage                             [PYTHON] │
   │ пишет ответ заказчику по final_status; для REJECT        │
   │ основание выбирается по типу риска                       │
   │ → BriefAnalysisResultBuilder собирает публичный JSON     │
   └──────────────────────────────────────────────────────────┘
        │
        ▼
   РЕЗУЛЬТАТ: BriefAnalysisResult → JSON в stdout
```

1. `BriefInputFactory` загружает текст или UTF-8 файл и нормализует пробелы.
2. `EmptyBriefRejectionStage` отклоняет пустой или очевидно бессмысленный ввод
   без LLM-вызова.
3. `SecurityGateStage` проверяет prompt injection, санитизирует PII и при
   блокировке завершает pipeline публичным reject-результатом без LLM.
4. `Extractor` извлекает фактические данные в `ExtractedBrief`.
5. `CompletenessCheckStage` проверяет обязательные поля из `config/criteria.yaml`.
6. `AssessmentStage` оценивает критерии, риски и Traffic Light за один LLM-вызов. Если бриф попал
   в список запрещённых тем из `config/criteria.yaml`, этап отвечает детерминированно
   и модель не вызывает.
7. `DeterministicArbiterStage` вычисляет итоговую рекомендацию по правилам.
8. `TemplateQuestionGeneratorStage` генерирует вопросы без LLM-вызовов.
9. `MVPPlannerStage` вызывает LLM только если Arbiter вернул `SIMPLIFY`.
10. `ResponseWriterStage` детерминированно формирует черновик ответа заказчику на русском языке.

Типичная стоимость LLM:

- Бриф по запрещённой теме: только `Extractor` = 1 LLM-вызов.
- Готовый бриф или бриф с уточнениями: `Extractor` + `Assessment` = 2 LLM-вызова.
- Бриф, которому нужно упрощение: `Extractor` + `Assessment` + `MVPPlanner` = 3 LLM-вызова.

`EmptyBriefRejectionStage`, `SecurityGateStage`, `CompletenessCheckStage`,
`DeterministicArbiterStage`, `TemplateQuestionGeneratorStage` и
`ResponseWriterStage` работают без LLM.

## Конфигурация

Создайте `.env` на основе `.env.example`:

```env
# Провайдер LLM. Подходит любой OpenAI-совместимый API — адрес задаётся явно.
LLM_API_KEY=your_key
LLM_MODEL=openai/gpt-4o-mini
LLM_BASE_URL=https://openrouter.ai/api/v1

LANGFUSE_PUBLIC_KEY=
LANGFUSE_SECRET_KEY=
LANGFUSE_HOST=https://cloud.langfuse.com
DEBUG=false
LOG_LEVEL=INFO
```

Обязательны только `LLM_API_KEY`, `LLM_MODEL` и `LLM_BASE_URL` — без них приложение
не стартует.

### Настройка вызовов LLM

Эти переменные необязательны: у каждой есть значение по умолчанию в `Settings`.
Держите в `.env` только те, что действительно отличаются от дефолта — иначе значение
окажется записано дважды, и `.env` будет молча перекрывать код. Полный список
с пояснениями лежит в `.env.example`.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `LLM_TEMPERATURE` | `0.0` | Насколько случаен выбор слова, от `0` до `2` |
| `LLM_MAX_TOKENS` | не задан | Предел длины ответа |
| `LLM_TOP_P` | не задан | Отбрасывает маловероятные слова, от `0` до `1` |
| `LLM_MAX_ATTEMPTS` | `2` | Число попыток запроса |
| `LLM_TIMEOUT_SECONDS` | `60.0` | Таймаут одной попытки |
| `LLM_TRANSPORT_RETRIES` | `0` | Повторы внутри SDK `openai` |

Пустое значение не означает «по умолчанию»: строка `LLM_MAX_TOKENS=` не пройдёт
валидацию и приложение не запустится. Чтобы остаться на дефолте, уберите строку
целиком или закомментируйте её.

#### `LLM_MAX_TOKENS` и `LLM_TOP_P` — про разное

`LLM_MAX_TOKENS` управляет **длиной**. Это жёсткий предел: дойдя до него, модель
обрывает ответ на полуслове. Она не начинает писать короче — её просто прерывают.
Для этого проекта важно, что все этапы просят структурированный JSON: обрыв даёт
не короткий ответ, а сломанный JSON, запрос уходит на повтор и в итоге падает
с ошибкой. Ставьте значение с запасом — это страховка от неожиданно длинного
ответа и лишних трат, а не способ управлять стилем.

`LLM_TOP_P` управляет **выбором слова** и на длину не влияет никак. На каждом шаге
модель прикидывает вероятность каждого возможного следующего слова и выстраивает
их от самого вероятного к самому редкому. Значение `0.9` означает: бери варианты
с начала списка, пока их суммарная вероятность не наберёт 90%, а весь оставшийся
«хвост» редких слов отбрось и выбирай только из отобранных. Чем меньше значение,
тем предсказуемее и суше текст; `1.0` не отбрасывает ничего.

Учтите, что `LLM_TOP_P` и `LLM_TEMPERATURE` управляют одним и тем же — случайностью
выбора, поэтому менять принято что-то одно. При нашем дефолте `LLM_TEMPERATURE=0.0`
модель и так каждый раз берёт самое вероятное слово, так что `LLM_TOP_P` в этой
конфигурации практически ни на что не влияет.

Две настройки легко перепутать:

- `LLM_MAX_ATTEMPTS` — **общее** число попыток, а не число повторов: при `2` уходит
  два запроса, а не три.
- `LLM_TRANSPORT_RETRIES` — ретраи внутри SDK `openai`, поверх наших попыток. При `0`
  за повторы отвечает один слой и таймаут считается честно; при `2` (прежнее поведение
  SDK по умолчанию) один неудачный вызов может обернуться шестью запросами к провайдеру.

Критерии проекта, обязательные поля, типы рисков, список запрещённых тем и правила
арбитража находятся здесь:

```text
config/criteria.yaml
```

Traffic Light хранится отдельно и используется как конфигурация соответствия задач
навыкам студентов:

```text
config/traffic_light.yaml
```

`AssessmentStage` получает этот конфиг через `TrafficLightLoader`, возвращает
`AssessmentResult.traffic_light`, а `DeterministicArbiterStage` использует
`traffic_light.status` как один из сигналов арбитража.

Шаблоны уточняющих вопросов находятся здесь:

```text
config/question_templates.json
```

Русские названия обязательных полей брифа находятся здесь:

```text
config/field_titles.json
```

Бизнес-критерии намеренно вынесены в конфигурацию и не зашиты жёстко в промпты
или Python-логику принятия решений.

`config/criteria.yaml` — внутренний англоязычный конфиг. Его `title` и `description`
нужны для отладки и трассировки и не должны попадать в текст, который читает заказчик:
письмо и публичный результат собираются из русских формулировок оценки и из
`config/field_titles.json`.

## Запуск

Анализ текста из командной строки:

```bash
python -m app.main --text "Нужно сделать сайт для образовательного проекта..."
```

Анализ UTF-8 файла:

```bash
python -m app.main --file path/to/brief.txt
```

Только нормализация ввода без вызова LLM:

```bash
python -m app.main --text "Текст брифа" --normalize-only
```

## Результат

CLI возвращает JSON, соответствующий публичной Pydantic-модели
`BriefAnalysisResult` из `app/schemas/final_result.py`:

```json
{
  "summary": "Краткое описание проекта",
  "extracted_fields": {
    "goal": "Цель проекта",
    "expected_result": "Ожидаемый результат",
    "tasks": ["Задача 1"],
    "domain": "Предметная область",
    "direction": "development",
    "available_materials": ["Данные", "Макеты"],
    "missing_information": ["Что не указано"],
    "complexity_factors": ["Что усложняет проект"]
  },
  "assessment": {
    "recommendation": "accept",
    "confidence": "high",
    "reasons": ["Почему дана рекомендация"],
    "risks": ["Риски проекта"]
  },
  "clarifying_questions": ["Вопрос заказчику"],
  "mvp_suggestion": "Предложение по упрощению проекта",
  "customer_response_draft": "Черновик ответа заказчику"
}
```

`extracted_fields.direction` is one of `development | design | analytics | marketing | ai | education | mixed | unknown`.
`mixed` means the project combines several directions; `unknown` means the direction could not be reliably classified in the public taxonomy.

Public JSON Schema результата находится в `schemas/brief_analysis_result.schema.json`.
Для обновления схемы из Pydantic-модели используйте:

```bash
python scripts/generate_public_schema.py
```
