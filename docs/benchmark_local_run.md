# Замер качества на локальной модели

Инструкция по запуску бенчмарка через LM Studio: что настроить, чем запускать, что получится
на выходе и как это читать.

Проверялось на RTX 3070 (8 ГБ) и датасете `synt_data_labeled.csv` — 75 размеченных брифов,
шесть классов.

---

## 1. Главное ограничение: не размер модели, а размер промпта

Промпт этапа `assessment` — около **13 тысяч токенов**. В него целиком вкладываются
`config/criteria.yaml` (18.7 КБ JSON), `config/traffic_light.yaml` (15.5 КБ JSON) и JSON Schema
ответа (6 КБ). Отсюда растут все требования ниже: видеопамять расходуется в основном на KV-кэш
под этот промпт, а не на веса модели.

Второй важный момент: пайплайн жёстко просит `response_format: {"type": "json_schema", "strict": true}`
(см. `_with_json_schema_response_format` в `app/llm/runner.py`). LM Studio это умеет — собирает
из схемы GBNF-грамматику и заставляет модель выдавать валидный JSON. Модель без поддержки
structured output здесь просто не заработает.

## 2. Что скачать

Качать в порядке списка, начиная с первой.

| Модель | Квант | Размер | Зачем именно она |
|---|---|---|---|
| **Qwen3-4B-Instruct-2507** | Q5_K_M | ~2.9 ГБ | Основной кандидат. Не «размышляющая», влезает в 8 ГБ с контекстом 32k и запасом, уверенно держит strict JSON schema, приличный русский |
| **Qwen3-8B** | Q4_K_M | ~5.0 ГБ | Потолок качества, который ещё помещается в 8 ГБ. Контекст только 16k, скорость примерно вдвое ниже, режим thinking надо отключать явно |
| **RuadaptQwen3-4B-Instruct** | Q5_K_M | ~3.0 ГБ | Расширенный русский токенизатор: те же 13k промпта укладываются в заметно меньшее число токенов, то есть выигрыш и по времени, и по расходу |

Ориентир по времени: полный прогон 75 брифов на 4B-модели — примерно 40–60 минут, на 8B — вдвое дольше.

Модели с «размышлениями» (thinking / reasoning) в этой задаче вредны: они тратят сотни токенов
до начала JSON, из-за чего метрика «токенов на бриф» перестаёт что-либо значить, а время растёт.
Если берёте такую модель — отключайте режим размышлений.

## 3. Настройки загрузки модели в LM Studio

Задаются при загрузке модели, **до** старта сервера.

| Параметр | Значение | Почему |
|---|---|---|
| **Context Length** | не меньше `16384`, лучше `20480` | Промпт `assessment` ~13k токенов. При дефолтных 4096 он не помещается — это самая частая причина, по которой «ничего не работает» |
| **Flash Attention** | включить | Заметно сокращает память под KV-кэш |
| **K/V Cache Quantization** | `Q8_0` | На 8 ГБ это разница между «влезло в видеопамять» и «уехало в оперативную», а значит между минутами и часами |
| **GPU Offload** | все слои | Если часть слоёв осталась на процессоре — прогон растянется в разы |

Дальше поднимается локальный сервер (вкладка Developer / Local Server), по умолчанию на порту 1234.

## 4. Настройки в `.env`

```
LLM_BASE_URL=http://localhost:1234/v1
LLM_API_KEY=lm-studio
LLM_MODEL=<идентификатор модели, как он показан в LM Studio>
LLM_TIMEOUT_SECONDS=300
```

Что и почему:

- **`LLM_API_KEY`** — LM Studio ключ не проверяет, но поле обязательное в `app/config/settings.py`,
  поэтому пишем любую непустую строку.
- **`LLM_TIMEOUT_SECONDS=300`** — обязательно. Дефолтные 60 секунд рассчитаны на облако; локальная
  модель с промптом в 13k токенов в них не укладывается, и прогон превратится в череду таймаутов.
- **`LLM_TEMPERATURE`** — не трогать, дефолт `0.0`. Нужен ради воспроизводимости: иначе два прогона
  одной модели дадут разные цифры и сравнивать будет нечего.
- **`LLM_TRANSPORT_RETRIES`** — не трогать, дефолт `0`. Это повторы внутри SDK, они перемножаются
  с нашими `LLM_MAX_ATTEMPTS`. При ненулевом значении один неудачный вызов может обернуться шестью
  запросами, и расход токенов станет неинтерпретируемым.

Пустое значение не означает «по умолчанию»: строка вида `LLM_MAX_TOKENS=` не пройдёт валидацию
и приложение не запустится. Чтобы остаться на дефолте — не пишите строку вовсе.

## 5. Как запускать

Прогон датасета через боевой пайплайн:

```bash
env/bin/python -m benchmark.runner synt_data_labeled.csv benchmark/results/qwen3-4b.csv
```

Подсчёт метрик по полученным предсказаниям:

```bash
env/bin/python -m benchmark.metrics benchmark/results/qwen3-4b.csv
```

Полезные детали:

- **`--limit N`** — прогнать только первые N строк. Перед часовым прогоном стоит проверить связку
  на двух-трёх брифах: `--limit 3`.
- **Результаты пишутся построчно с немедленным сбросом на диск.** Если прогон прервался, уже
  посчитанные строки в CSV останутся.
- **Имя выходного файла — это ваша единственная пометка о том, какой моделью он получен.**
  Называйте по модели (`qwen3-4b.csv`, `qwen3-8b.csv`). Фактическое значение `LLM_MODEL` печатается
  в итоговой строке раннера — сверяйтесь с ней.
- **Смена модели** — загрузить другую в LM Studio, поправить `LLM_MODEL` в `.env`, запустить
  с новым именем выходного файла.
- **Первый бриф всегда дороже остальных** — на нём модель подтягивается в видеопамять. Смотрите
  на `latency_median_seconds`, а не только на среднее.

### Базовый прогон через облако — обязательно

Тот же раннер, но с прежними `LLM_BASE_URL` / `LLM_MODEL` в `.env`:

```bash
env/bin/python -m benchmark.runner synt_data_labeled.csv benchmark/results/cloud-baseline.csv
```

Без этой точки отсчёта нельзя отличить «пайплайн плохой» от «локальная модель слабая» — а это
ровно тот вопрос, ради которого всё затевается. По объёму это около 2 млн промпт-токенов, то есть
на gpt-4o-mini — копейки.

## 6. Что получится на выходе

### Файл предсказаний

CSV с колонками:

| Колонка | Что в ней |
|---|---|
| `id` | Идентификатор брифа из исходного датасета |
| `gold_class` | Класс из разметки |
| `predicted_class` | Что выдал пайплайн |
| `correct` | `true` / `false` |
| `error` | Текст исключения, если бриф упал. Пусто, если всё прошло |
| `latency_seconds` | Время обработки брифа. Пишется и для упавших: отвалившийся по таймауту бриф стоил столько же, сколько успешный |
| `llm_calls` | Сколько запросов к модели ушло на этот бриф |
| `prompt_tokens` / `completion_tokens` / `total_tokens` | Расход по этому брифу, включая ретраи |

Пустая ячейка в колонках расхода — это не ноль: значит, провайдер не сообщил цифры.

Число вызовов на бриф — от одного до трёх, и это нормально:

- **2 вызова** — обычный случай: `Extractor` + `Assessment`
- **3 вызова** — когда арбитр вернул `SIMPLIFY`, добавляется `MVPPlanner`
- **1 вызов** — когда сработал детерминированный матчер запрещённых тем и `Assessment` не понадобился
- **0 вызовов** — пустой бриф, его отсекает `EmptyBriefRejectionStage` до всякой модели

### Отчёт метрик

```
Summary:
  total_rows: 75            всего строк в файле
  evaluated: 71             строк, попавших в расчёт метрик
  skipped: 0                пропущено (пустой gold_class)
  errors: 4                 брифов упало с исключением
  correct / incorrect       верных и неверных предсказаний
  accuracy: 0.xxx           доля верных
  f1_macro: 0.xxx           главная метрика, см. ниже
  error_rate: 0.xxx         доля упавших от числа запущенных
  latency_mean_seconds      среднее время на бриф
  latency_median_seconds    медианное время на бриф
  llm_calls_per_brief       среднее число вызовов модели на бриф
  total_tokens_per_brief    средний расход токенов на бриф
```

Дальше идут три блока: **per-class metrics** (precision / recall / F1 / support по каждому из шести
классов), **confusion matrix** (строки — разметка, столбцы — предсказание) и список
**classification errors** вида `REJECT -> CLARIFY: 3`.

`f1_macro` — невзвешенное среднее F1 по классам, которые встретились в разметке **или** хотя бы раз
были предсказаны. Класс, которого нет ни там, ни там, в среднее не входит, чтобы не занижать метрику
за его отсутствие в срезе.

## 7. Как читать результат

**`error_rate` смотреть раньше, чем `f1_macro`.** Упавшие брифы выпадают из расчёта, и метрика
считается по уцелевшей подвыборке — то есть выглядит лучше, чем система работает. Если `error_rate`
заметный, сначала разберитесь с колонкой `error`, а уже потом сравнивайте качество.

**Классификатор детерминированный.** Финальный класс выдаёт `app/pipeline/arbiter.py` по правилам
из `config/criteria.yaml`, а не модель. Модель влияет только на вход арбитра: извлечённые факты,
риски, полнота, светофор. Поэтому матрица ошибок читается как диагностика извлечения фактов,
а не как «модель выбрала не тот класс».

**Рост столбца MENTOR_REVIEW — признак слабой модели.** Это дефолтный статус арбитра «не подошло
ни одно правило». Всё, что модель не смогла разобрать, стекается туда.

**Дисбаланс классов.** В датасете REJECT — 36 из 75 (48%), у остальных пяти классов support 7–10.
При таких размерах `f1_macro` очень шумный: одна-две строки двигают его на несколько пунктов.
Сравнивать модели только по нему нельзя — смотрите вместе с матрицей и `error_rate`.

**Три брифа пустые** (id 17, 40, 65, все размечены как `REJECT`). Их отсекает
`EmptyBriefRejectionStage` до обращения к модели, так что они дают гарантированно верный ответ
за ноль вызовов и слегка завышают recall по REJECT. При точном разборе их стоит исключить.

**Известный краш.** В `TODO_otkaznoe_pismo.md` описан
`BriefAnalysisResultError: Unable to classify public project direction` из `classify_direction`
(`app/pipeline/result_builder.py`), воспроизводимый на брифах с запрещёнными темами (крипта,
накрутка). Такие строки попадут в `error` и выпадут из метрик — это баг пайплайна, а не свойство
модели, и на локальном прогоне он проявится так же, как на облачном.

## 8. Если что-то пошло не так

| Симптом | Причина |
|---|---|
| Ошибки таймаута почти на каждом брифе | `LLM_TIMEOUT_SECONDS` остался равным 60 |
| Модель отвечает обрывками, ошибки `truncated_json` / `length_finish` | Context Length при загрузке модели меньше 16384, промпт не помещается |
| Прогон идёт часами, видеокарта почти не загружена | Часть слоёв осталась на процессоре либо KV-кэш не помещается: проверьте GPU Offload, Flash Attention и K/V Cache Quantization |
| Колонки `prompt_tokens` и `total_tokens` пустые | Рантайм не вернул `usage`. Само по себе не мешает считать качество и время, но расход измерить не выйдет |
| `Input CSV is missing required columns: brief` | В датасете колонка называется иначе. Раннер ждёт ровно `id`, `brief`, `gold_class` |
| `Missing required environment variables` | В `.env` нет одной из обязательных: `LLM_API_KEY`, `LLM_MODEL`, `LLM_BASE_URL` |
| Много ошибок валидации схемы | Модель не тянет `AssessmentPayload` — вложенные `$defs` и ограничения, которые грамматика не проверяет, а pydantic проверяет. Это повод пробовать модель крупнее |
