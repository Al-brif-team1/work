# ТЗ для студентов Data Science: ИИ-ассистент оценки проектных брифов «Мастерской»

### 1. Контекст

«Мастерская» получает заявки от внешних заказчиков на студенческие проекты. Заказчик заполняет бриф: описывает компанию, направление, идею проекта, задачи, наличие материалов и дополнительную информацию.
Менеджеры «Мастерской» должны понять:


- можно ли превратить заявку в реалистичный студенческий проект; 
- каких данных не хватает; 
- какие вопросы задать заказчику; 
- как упростить проект, если он слишком большой; 
- какой корректный ответ отправить заказчику. 



Сейчас эта оценка во многом выполняется вручную. Цель проекта — разработать ИИ-ассистента, который помогает менеджеру и наставнику быстрее и стабильнее анализировать брифы.

### 2. Цель студенческого проекта

Разработать production-ready Python-репозиторий с ИИ-функциональностью для анализа проектных брифов.


Решение должно принимать текст брифа, структурировать его, оценивать по критериям, выявлять риски, генерировать уточняющие вопросы, предлагать MVP-вариант и формировать черновик ответа заказчику.


Решение не должно самостоятельно принимать финальное решение за человека. Оно выдает рекомендацию и объяснение.

### 3. Что нужно реализовать

ИИ-ассистент должен выполнять следующие функции: 

1. **Первичный парсинг брифа**. Извлекать из неструктурированного текста:   
- цель проекта;   
- продукт или результат, который хочет заказчик;   
- ключевые задачи;   
- предметную область;   
- предполагаемое направление: разработка, дизайн, аналитика, маркетинг, ИИ, образование, смешанный проект;  
- наличие данных, макетов, API, контента, ссылок, исходных материалов;   
- ограничения по срокам, если они указаны;   
- признаки сложности и неопределенности. 

1. **Оценка брифа по критериям.** Система должна сопоставлять бриф с критериями «Мастерской» и выдавать рекомендацию:   
- проект можно брать;   
- нужны уточнения;   
- проект слишком большой, нужен MVP;   
- нужна экспертиза наставника;   
- проект не подходит.   

2. **Генерация уточняющих вопросов.** Ассистент должен формировать конкретные вопросы к заказчику, например:   
- какие данные уже есть;   
- есть ли доступ к API;   
- кто будет давать материалы;   
- какой ожидается конечный результат;   
- какие функции обязательны для первой версии;   
- есть ли макеты, брендбук, аналитика, контент, ограничения.   

3. **Упрощение слишком широкого проекта.** Если заявка слишком объемная, ассистент должен предложить реалистичный MVP:   
- какие функции оставить;   
- какие функции исключить из первой версии;   
- что можно сделать силами студентов;   
- что требует отдельного промышленного проекта.   

4. **Генерация ответа заказчику.** Ассистент должен генерировать черновик корректного ответа:   
- если проект подходит;   
- если нужны уточнения;   
- если проект можно взять только в сокращенном виде;   
- если проект не подходит;   
- если нужна дополнительная экспертиза.



### 4. Важное ограничение

Критерии оценки «берем / не берем / уточняем / упрощаем» должны быть дополнительно уточнены у команды «Мастерской».
Студенты должны предусмотреть в решении отдельный конфигурационный слой для критериев: например YAML/JSON-файл или Python-конфиг. Критерии не должны быть жестко зашиты в промпты и код так, чтобы их нельзя было быстро изменить.

### 5. Ожидаемый формат результата по одному брифу

**Решение должно возвращать структурированный результат, например JSON:**

```json
{

"summary": "Краткое описание проекта",

"extracted_fields": {

"goal": "Цель проекта",

"expected_result": "Ожидаемый результат",

"tasks": ["Задача 1", "Задача 2"],

"domain": "Предметная область",

"direction": "development | design | analytics | marketing | ai | education | mixed",

"available_materials": ["Данные", "Макеты", "Ссылки"],

"missing_information": ["Что не указано"],

"complexity_factors": ["Что усложняет проект"]

},

"assessment": {

"recommendation": "accept | clarify | simplify | mentor_review | reject",

"confidence": "low | medium | high",

"reasons": ["Почему дана такая рекомендация"],

"risks": ["Риски проекта"]

},

"clarifying_questions": ["Вопрос 1", "Вопрос 2"],

"mvp_suggestion": "Предложение по упрощению проекта",

"customer_response_draft": "Черновик ответа заказчику"

}
```



### 6. Архитектурные требования

Студенты должны реализовать именно ИИ-ядро, а не полноценный пользовательский сервис.

Репозиторий должен включать:

- Python-пакет с основной логикой;
- модуль загрузки и нормализации брифа;
- модуль LLM-анализа;
- модуль оценки по критериям;
- модуль генерации вопросов;
- модуль генерации MVP-рекомендаций;
- модуль генерации ответа заказчику;
- конфигурацию критериев;
- CLI или простой Python-интерфейс для запуска анализа;
- тесты;
- README с инструкцией запуска.

Допустимо использовать внешние LLM API. При этом код должен быть устроен так, чтобы модель можно было заменить без переписывания бизнес-логики.



### 7. Рекомендуемый путь реализации



**Минимальный уровень:**

- последовательный LLM-пайплайн из нескольких шагов;
- structured output в JSON;
- конфигурационные критерии;
- тестовые примеры;
- CLI-запуск анализа одного брифа.



**Продвинутый уровень:**

- агентная схема с отдельными ролями:
- extractor;
- evaluator;
- risk analyst;
- question generator;
- response writer;
- self-check результата;
- проверка полноты JSON;
- автоматическая валидация ответа по схеме;
- сравнение нескольких моделей или промптов.

Главное — качество результата, а не сложность агентной архитектуры.



### 8. Требования к качеству ИИ-ответов

Ассистент должен:

- не выдумывать отсутствующие сведения;
- явно указывать, что неясно;
- отделять факты из брифа от предположений;
- не делать финальное решение за человека;
- объяснять рекомендацию;
- формировать практичные вопросы, а не общие фразы;
- предлагать реалистичный MVP;
- писать ответ заказчику в деловом и бережном тоне;
- помечать случаи, где нужна экспертиза наставника.



### 9. Что не входит в задачу студентов

В задачу не входит:

- разработка полноценного веб-интерфейса;
- CRM;
- личный кабинет менеджера;
- автоматическая отправка писем;
- интеграции с Telegram, почтой или базами «Мастерской»;
- финальное бизнес-решение по проекту;
- разметка исторической базы заявок как обязательная часть поставки.



### 10. Критерии приемки

Проект считается выполненным, если:

- репозиторий запускается по README;
- можно передать на вход один бриф и получить структурированный результат;
- результат валидируется по JSON-схеме;
- рекомендации объяснимы;
- уточняющие вопросы соответствуют проблемам конкретного брифа;
- для слишком широких проектов предлагается MVP;
- код покрыт базовыми тестами;
- критерии оценки можно изменить без переписывания основной логики;
- API-ключи и настройки вынесены в переменные окружения или конфиг;
- решение можно встроить в будущий сервис как отдельный Python-модуль.



### 11. Итоговые артефакты

Студенты должны передать:

- Git-репозиторий с кодом;
- README;
- пример .env.example;
- конфиг критериев;
- JSON-схему результата;
- несколько синтетических тестовых брифов;
- unit/integration tests;
- краткий документ с описанием архитектуры;
- демонстрационный запуск на 2-3 примерах.
