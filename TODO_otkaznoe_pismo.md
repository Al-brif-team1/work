# Доработки отказного письма

Задачи по тексту письма, который получает заказчик при вердикте REJECT.
Сам отказ всегда работал правильно — вопрос был только в том, **как он объясняется
заказчику**.

## Сделано 2026-09-06

Оснований для отказа три, и они различаются типом риска в `assessment_result.risks`.
Раньше на все три собиралось одно письмо: блок «Основания оценки» со всеми проваленными
критериями и концовка «подготовить новый бриф с более ограниченным объёмом». Заказчик
делал вывод, что достаточно дослать материалы и сократить объём, — а для запрещённой темы
и для предложения о партнёрстве это неверно.

Теперь `_reject_response` (`app/pipeline/response_writer.py`) определяет основание по типу
риска (только `high` и `critical`, при нескольких — по `_REJECT_GROUND_PRIORITY`):

| Риск | Письмо |
|---|---|
| `restricted_topic` | «Проект относится к направлению, с которым Мастерская Яндекс Практикума не работает.» — письмо целиком, без блока оснований |
| `out_of_scope_request` | «Запрос относится к формату, которого нет среди поддерживаемых проектных направлений.» — письмо целиком, без блока оснований |
| `production_criticality` | обычное письмо, но концовке предшествует «Ответственность за результат здесь выше той, что можно доверить студенческой команде.» |
| прочие отказы, в том числе `reject_by_traffic_light_red` | без изменений |

Название темы и сработавший фрагмент брифа заказчику не показываются, хотя
`build_restricted_topic_assessment` их собирает: в публичном JSON и в трейсах они
остаются. У `production_criticality` приглашение переписать бриф сохранено сознательно —
снизить цену ошибки реально, дверь там не закрывается.

Подробности: `docs/architecture_explained.md`, раздел «Три основания отказа и три письма».

## Рядом, но не про письмо

### Направления захардкожены в коде

Заявка о создании курса получает `direction: development`. Направления лежат в
`_DIRECTION_VALUES` и `_FALLBACK_DIRECTION_SIGNALS` (`app/pipeline/result_builder.py:29-37`),
из конфига берутся только алиасы. Отдельная задача, к тексту письма отношения не имеет.

Связанное падение на неопознанном направлении (`Unable to classify public project
direction`) **уже вылечено**: `classify_direction` возвращает `unknown`
(`result_builder.py:195`), и публичная схема это значение принимает
(`tests/test_response_writer.py:556`). Перенос таблицы направлений в конфиг остаётся.

### `LLM_MAX_TOKENS=512` роняет пайплайн на любом брифе

Замечено 2026-08-29 на запрещённых темах и списано на фильтр провайдера по содержимому:

```
LLMRunnerProviderError: LLM request failed after 2 attempts
ExtractorError: Unable to extract brief structure after 2 attempts
```

2026-09-06 причина найдена, и дело не в содержимом. С `LLM_MAX_TOKENS=512` из `.env`
ответ модели обрывается на середине, `generate_json` не может его разобрать
(`app/llm/openrouter.py:74`) и стадия падает. Воспроизводится на любом брифе, включая
безобидный барбершоп. С `LLM_MAX_TOKENS=8000` и `LLM_TIMEOUT_SECONDS=240` все три
проверочных брифа проходят пайплайн целиком.

Что делать: поднять `LLM_MAX_TOKENS` в `.env` и `.env.example` до рабочего значения,
а поверх — сделать так, чтобы обрыв по лимиту токенов отличался в логах от невалидного
JSON: сейчас обе ситуации выглядят одинаково и уводят диагностику не туда.

Аргумент про гейт до `Extractor` при этом остаётся в силе: детерминированная проверка
запрещённых тем стоит после извлечения, так что на части брифов до неё дело может не
дойти. Отказались от переноса из-за контракта финального JSON
(`BriefAnalysisResultBuilder._validate_context` требует все четыре результата).

## Как проверить письма

```bash
env/bin/python -m unittest tests.test_response_writer
```

Живой прогон (с рабочим лимитом токенов, см. выше):

```bash
LLM_MAX_TOKENS=8000 LLM_TIMEOUT_SECONDS=240 env/bin/python -m app.main --text "Нужна криптобиржа с P2P-обменом и кошельком для токенов."
LLM_MAX_TOKENS=8000 LLM_TIMEOUT_SECONDS=240 env/bin/python -m app.main --text "Здравствуйте! Предлагаем сотрудничество: хотим совместно с Практикумом создать и разместить курс по нашему продукту для ваших студентов."
LLM_MAX_TOKENS=8000 LLM_TIMEOUT_SECONDS=240 env/bin/python -m app.main --text "Нужен телеграм-бот для записи клиентов в барбершоп: запись, напоминания, выгрузка в таблицу."
```

Смотреть `customer_response_draft`: у первых двух — одна фраза без блока оснований,
у третьего письмо не изменилось.
